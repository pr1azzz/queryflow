# ПР10 — шпаргалка по 30 пунктам таблицы оценивания

Источник: §7.3, страницы 175–179 PDF ПР10.

Все примеры относятся к QueryFlow. Номера ниже соответствуют строкам таблицы оценивания, а не разделу «Контрольные вопросы».
Команды запускайте из корня проекта с активированным `.venv`. Адрес сайта: `http://127.0.0.1:8000/` при обычном `python manage.py runserver`.
Если сервер запущен на другом порту, используйте его адрес. Сохраняйте файл после изменения и обновляйте нужную страницу.
Учебные изменения кода возвращайте после демонстрации; для CRUD создавайте отдельные тестовые записи.
Участник `participants.User` — автор вопросов и ответов; учётная запись Django Admin — отдельная модель авторизации.

Для примеров ORM откройте `python manage.py shell` и выполните:

```python
from categories.models import Category
from participants.models import User
from questions.models import Question
from answers.models import Answer
from django.db.models import Count, F, Q
```

Контрольная точка ПР10: `147eea1`. Примеры описывают текущую версию; появившиеся в ПР11 формы обозначены явно.

## 1. Настройка административной панели

Войдите в `/admin/` и откройте вопросы. Столбцы задаёт list_display, поиск — search_fields, фильтры — list_filter, порядок — ordering, число строк — list_per_page. Найдите вопрос по имени автора или категории и отфильтруйте по статусу. Код: `questions/admin.py`; зарегистрированы все четыре модели.

## 2. Связанные объекты и inline

Откройте категорию или участника в админке: QuestionInline показывает вопросы. У вопроса AnswerInline показывает ответы. extra=0 убирает лишние пустые строки, show_change_link открывает отдельную карточку. ForeignKey связывает запись с родителем, PROTECT защищает используемого родителя от удаления.

## 3. Изменение модели и миграция

Покажите модели и файлы migrations. Безопасный пример — изменение verbose_name с созданием и просмотром AlterField. makemigrations создаёт описание, migrate применяет его. После показа верните параметр и создайте следующую миграцию; не переписывайте применённую историю.

## 4. Миграция существующих значений

Откройте `questions/migrations/0002_question_status.py`: AddField(status), RunPython, RemoveField(is_closed). False переходит в open, True — в closed; существующие ID и связи сохраняются. Используется apps.get_model() для исторической модели. Обратное преобразование теряет отдельный смысл withdrawn, потому что старое поле булево.

## 5. Django Shell

`python manage.py shell`, затем `Question.objects.first()` и `Question.objects.values("id", "text", "status")`. Для изменения используйте тестовую категорию: измените имя в памяти, сравните с повторным get, затем сохраните save(). Сохранённое и несохранённое состояния различаются.

## 6. Создание, изменение и удаление ORM

Выполните `python manage.py orm_demo`: команда создаёт тестовую категорию, изменяет её, читает через get и удаляет. Вся демонстрация дополнительно обёрнута транзакцией с откатом. В коде видны create(), save(update_fields=...), get(), delete(), exists(). Рабочие записи не изменяются.

## 7. Несколько условий QuerySet

`Question.objects.active().filter(category_id=1, author_id=1)` — открытые вопросы конкретного автора в категории. Для даты добавьте `.for_date("2026-09-19")`. Условия соединяются AND. В браузере тот же результат задаётся полями формы списка.

## 8. Поля связанных моделей

`Question.objects.filter(category__name__icontains="Python")` ищет по категории, `author__name__icontains` — по имени автора. Двойное подчёркивание задаёт переход по связи. Сравните с category_id=1, где условие относится непосредственно к хранимому внешнему ключу.

## 9. Собственный QuerySet

В `questions/models.py` объявлен QuestionQuerySet и подключён через as_manager(). Методы active(), cancelled(), completed(), for_date() возвращают QuerySet, поэтому объединяются цепочкой. В QueryFlow это открытые, отозванные и закрытые вопросы. `.active().for_date("2026-09-19")` демонстрирует совместную работу.

## 10. Проверка ввода

Текущая QuestionFilterForm проверяет ChoiceField, DateField, ModelChoiceField и IntegerField. На `/questions/?date=wrong` появляется 400 с ошибкой формы. В ПР10 до добавления Form проверку выполнял parse_parameters(). В ORM попадают только проверенные ID, даты и разрешённые ключи.

## 11. Динамическая сортировка

`SORTS` в `questions/queries.py` связывает ключи newest/oldest/category/author с полями order_by(). Выберите «По автору», затем «Сначала старые». Неизвестный sort вызывает 400, а не FieldError. Вторичное поле pk обеспечивает устойчивый порядок одинаковых значений.

## 12. values

Покажите question_rows(): выбираются id, text, category_id, author_id, status и дополнительные поля. В shell выполните `Question.objects.values("id", "text")`, добавьте "status" и сравните словари. Шаблон должен использовать реальные ключи результата, а не свойства объекта модели.

## 13. annotate и F

`category_name=F("category__name")`, `author_name=F("author__name")` в question_rows() присваивают имена связанным значениям. `answers_count=Count("answers")` добавляет число ответов. F вычисляется в SQL и не копирует имя автора в новую сохранённую колонку вопроса.

## 14. Обработка отсутствия

В question_detail(), category_detail(), answer_detail() используется get_object_or_404(). Откройте существующий и несуществующий ID. Для category дополнительно проверьте `/categories/topic/no-such-topic/`. Ожидается статус 404; DEBUG определяет оформление страницы, но не результат.

## 15. slug и get_absolute_url

У Category есть уникальное поле slug. get_absolute_url() вызывает reverse("categories:by_slug", args=[self.slug]). Маршрут: `topic/<slug:slug>/`. Откройте категорию из списка или нажмите «Смотреть на сайте» в админке. Старый маршрут по числовому ID сохранён. Менять slug нужно осознанно: старый адрес перестанет находить запись.

## 16. GeneratedField

У Question поле text_length = GeneratedField(expression=Length("text"), db_persist=True). SQLite вычисляет число символов и сохраняет результат. На тестовом вопросе измените текст, сохраните и выполните refresh_from_db(): длина изменится. В админке поле только для чтения. Это не обычное свойство Python.

## 17. Агрегаты по статусам

Откройте statistics_context() и `/questions/statistics/`: total=Count("pk"), отдельные Count с Q(status=...). Измените статус тестового вопроса через админку и обновите статистику. Общее количество не меняется, распределение по статусам меняется; отзыв не удаляет запись.

## 18. Группы и отбор групп

`Category.objects.annotate(questions_count=Count("questions")).filter(questions_count__gte=minimum)` считает вопросы по категориям. minimum=0 сохраняет пустые группы, minimum=1 убирает их. ORDER BY управляет порядком групп; HAVING в SQL соответствует фильтрации по агрегату.

## 19. Оптимизация select_related

На `/questions/1/` откройте SQL-панель Toolbar. Запрос карточки соединяет questions, categories и participants. Благодаря select_related("category", "author") шаблон получает category.name и author.name без отдельных запросов. Автотест проверяет ровно один запрос для загрузки вопроса с этими связями.

## 20. Анализ SQL в Debug Toolbar

Запустите с DEBUG=True, откройте `/questions/` с локального адреса и панель SQL справа. В анонимном запросе без фильтров проверено 5 запросов: COUNT для пагинации, страница карточек, общий счётчик категорий, варианты категорий и авторов. Авторизация или фильтры могут добавить запросы. Смотрите назначение каждого, а не только итоговую цифру.

## 21. Фильтрация, сортировка, пагинация

Временно PAGE_SIZE=1, выберите статус или категорию, порядок oldest, перейдите дальше. URL сохраняет параметры благодаря querystring. Paginator получает уже подготовленную выборку. После демонстрации верните PAGE_SIZE=10.

## 22. Доступность с учётом даты и статуса

В QueryFlow аналог — вопросы, ожидающие ответа: `/questions/unanswered/?date=2026-09-19`. В выборку входят только открытые вопросы без ответов на указанную дату. Отзыв или закрытие убирает вопрос из этой выдачи; добавление ответа тоже убирает его. В ПР11 дополнительно проверяется запрет одинакового открытого вопроса у автора. Бронирования помещений в наш проект не добавляются.

## 23. Контекстный процессор

`homepage/context_processors.py`, site_info() возвращает site_name и active_category_count; регистрация — в TEMPLATES настроек. Откройте главную, вопросы, ответы: общий подвал показывает число активных тем. В отличие от контекста отдельного view, процессор доступен всем шаблонам, отрисованным с request.

## 24. TextChoices

Покажите Question.Status: OPEN, CLOSED, WITHDRAWN, их хранимые значения и русские подписи. В админке измените статус тестового вопроса; проверьте список, карточку и статистику. QuerySet сравнивает значения с константами, а не разбросанными строками. Отозванный вопрос остаётся в базе.

## 25. Связанные значения одним запросом

question_rows() использует annotate(F(...)) и values(): автор и категория приходят в словаре. В Toolbar нет отдельного запроса на каждого автора каждой карточки. select_related нужен для объектов модели, когда дальше обращаются к их связям; в этом словарном запросе JOIN уже обеспечивает F.

## 26. Изменение исходных данных

На тестовом вопросе поменяйте текст в админке, сохраните и посмотрите text_length. Изменение имени категории сразу отображается на связанных карточках после обновления страницы: имя читается по связи. Для Python-объекта, загруженного раньше, нужен refresh_from_db() или новый запрос.

## 27. Именованные маршруты

В шаблонах используются `{% url "questions:detail" question.id %}` и Category.get_absolute_url(). Покажите `questions/urls.py` и `categories/urls.py`, перейдите из списка в карточку. Если переименовать маршрут только в urls.py и не обновить ссылки, возникнет NoReverseMatch. Число аргументов должно совпадать с маршрутом.

## 28. Обработка ошибки БД

В текущей версии ПР11 `queryflow/form_views.py` ловит IntegrityError вне transaction.atomic(): конфликт возвращает форму с общей ошибкой, DatabaseError — форму со статусом 503. Для безопасной демонстрации: `python -m pytest tests/test_forms.py -k database_failure -v`. Тест подменяет save(), а не повреждает рабочую БД. В этапе ПР10 проверки ошибок структуры выполнялись миграциями и ограничениями.

## 29. Проверка моделей и миграций

`python manage.py makemigrations --check` должно сообщить No changes detected; `python manage.py check` — отсутствие ошибок. Первая команда сравнивает модели с миграциями, вторая проверяет конфигурацию. Применение миграций подтверждает `showmigrations` с [X].

## 30. Автоматизированный сценарий

Откройте `tests/test_admin_orm.py`: test_status_managers_cancel_and_statistics проверяет отзыв, исключение из открытых и статистику; test_list_query_count_does_not_grow_with_records — отсутствие роста запросов на карточку. Запуск: `python -m pytest tests/test_admin_orm.py -v`. Тесты работают с отдельной БД.
