# ПР5 — ответы на 25 вопросов для защиты QueryFlow

Источник: таблица оценивания в §7.5 «ПР5_Django_Base.pdf», страницы 47–49.
**25 × 0,05 = 1,25 балла.** Здесь разобрана именно таблица оценивания,
а не отдельный список из 52 контрольных вопросов в §8.

В методичке используется Roomly. В моём варианте №245 используется
**QueryFlow — система учёта вопросов и ответов**. Аналоги примера:
`Room` → `Question`, `/rooms/` → `/questions/`,
`room_detail()` → `question_detail()`, `find_room_by_id()` →
`get_question_by_id()`. Дополнительно реализованы категории и ответы.
Поля `capacity` здесь нет: вместо него показываю реальные поля проекта.

Пути ниже отсчитываются от корня репозитория. Команды выполняются
в PowerShell с активированным `.venv`; без активации заменить `python`
на `.\.venv\Scripts\python.exe`.

## 1. Django-проект и Django-приложение

**Вопрос:** где настройки проекта и код приложений, чем они отличаются,
почему страницы разделены между приложениями?

**Ответ:** Django-проект объединяет настройки и приложения в один сайт.
Конфигурация находится в пакете [queryflow/](queryflow/):
`settings.py`, `urls.py`, `wsgi.py`, `asgi.py`. Django-приложение отвечает
за отдельную часть функциональности. `homepage` показывает главную страницу,
`questions` — вопросы, `categories` — категории, `answers` — ответы.
Разделение помогает держать маршруты и обработчики одной задачи рядом.
Приложение можно развивать отдельно, а проект связывает их.

**Показать:** дерево проекта, [queryflow/settings.py](queryflow/settings.py)
и [questions/views.py](questions/views.py). Корневой каталог репозитория
и вложенный пакет `queryflow/` имеют одинаковое имя, но разное назначение.

## 2. Проверка и запуск проекта

**Вопрос:** для чего нужен `manage.py`, как проверить и запустить проект?

**Ответ:** [manage.py](manage.py) — точка запуска управляющих команд Django.
Он задаёт `DJANGO_SETTINGS_MODULE=queryflow.settings` и передаёт аргументы
в `execute_from_command_line()`.

```powershell
python manage.py check
python manage.py runserver
```

Первая команда проверяет конфигурацию, вторая запускает сервер разработки
на `http://127.0.0.1:8000/`. Перед первым запуском выполняю
`python manage.py migrate` для служебных таблиц Django.
Сущности ПР3 при этом остаются в JSON. `runserver` предназначен для разработки.

## 3. Регистрация приложений

**Вопрос:** где приложения зарегистрированы и что будет без регистрации?

**Ответ:** в `INSTALLED_APPS` файла [queryflow/settings.py](queryflow/settings.py)
указаны `homepage.apps.HomepageConfig`, `questions.apps.QuestionsConfig`,
`categories.apps.CategoriesConfig`, `answers.apps.AnswersConfig`.
Конфигурации находятся в `apps.py` соответствующих приложений.

Без регистрации Django не включит приложение в реестр: не будет штатно
обнаруживать его модели, миграции, команды, шаблоны и статику средствами
обнаружения приложений. При этом простая view-функция без моделей **может
продолжить работать**, если её URLconf подключён через `include()`.
Регистрация приложения и подключение его URL — разные действия.

## 4. Структура приложений QueryFlow

**Вопрос:** какие приложения созданы, как распределены страницы и почему
нет отдельного приложения пользователей?

**Ответ:** `homepage` содержит `index()`, общий каркас `page()` и
`page_not_found()`. В `questions`, `categories`, `answers` находятся списки
и карточки соответствующих объектов. Всего реализовано семь видов страниц.

Отдельного приложения пользователей пока нет, потому что нет веб-сценариев
регистрации, входа или профиля. Класс [models/users.py](models/users.py)
сохранён из ПР3 и используется для отображения авторов: `question.author.name`
и `answer.author.name`. Это обычный Python-класс, он не является моделью
`django.contrib.auth.User`. Встроенный `auth` обслуживает служебные функции
Django, но не заменяет пользователей JSON-хранилища.

## 5. DEBUG и ALLOWED_HOSTS

**Вопрос:** что проверить перед отключением отладки и как влияют настройки?

**Ответ:** `DEBUG=True` включает технические страницы ошибок. При `False`
показывается пользовательский `handler404`. До отключения нужно задать
разрешённые хосты и убедиться, что обработчик существует в корневом URLconf.
У меня разрешены `localhost`, `127.0.0.1`, `[::1]`.

`ALLOWED_HOSTS` проверяет имя хоста запроса, а не URL-путь и не IP посетителя.
Недопустимый Host приводит к 400. Пустой список при `DEBUG=False` непригоден
для обычного запуска; `runserver` также требует непустой список.
При `DEBUG=True` и пустом списке есть специальное разрешение локальных хостов.

```powershell
$env:DJANGO_DEBUG = "False"
python manage.py runserver
# После остановки Ctrl+C:
Remove-Item Env:DJANGO_DEBUG
```

**Показать:** `/nonexistent/`. Собственные статические файлы `runserver`
при `DEBUG=False` по умолчанию не раздаёт. В ПР5 Bootstrap загружается
с CDN, собственный CSS встроен в `page()`.

## 6. Маршрутизация между URLconf

**Вопрос:** проследить `/rooms/999/` (в моём проекте `/questions/999/`).

**Ответ:** в [queryflow/urls.py](queryflow/urls.py) Django находит
`path("questions/", include("questions.urls"))`. Префикс `questions/`
уже обработан. Остаток `999/` проверяется в
[questions/urls.py](questions/urls.py) по `<int:question_id>/`.
Затем вызывается `question_detail(request, question_id=999)`.

`include()` передаёт оставшуюся часть пути в URLconf приложения,
а не вызывает представление самостоятельно. Параметры после `?`
не участвуют в сопоставлении шаблона пути.

## 7. Связь маршрута и view-функции

**Вопрос:** как ID передаётся в view, что менять при переименовании функции,
какова роль `name=`?

```python
path("<int:question_id>/", views.question_detail, name="detail")
```

**Ответ:** Django вызывает функцию со значением из URL как именованным
аргументом `question_id`. Её сигнатура —
`question_detail(request, question_id)`. Если переименовать функцию,
нужно обновить ссылку `views.question_detail` в `urls.py`; шаблон пути
может остаться прежним.

`name="detail"` — имя маршрута для построения ссылок. Вместе с
`app_name="questions"` получается `questions:detail`:

```python
reverse("questions:detail", args=[1])  # '/questions/1/'
```

Имя маршрута не обязано совпадать с именем функции. Если имя маршрута
сохраняется, вызовы `reverse()` менять не требуется.

## 8. Работа конвертера URL

**Вопрос:** почему `/questions/abc/` не вызывает `question_detail()`,
а `/questions/999/` может вызвать?

**Ответ:** `<int:question_id>` принимает цифры и преобразует значение в `int`.
`abc` не соответствует шаблону, поэтому до view запрос не дойдёт.
`999` соответствует шаблону и передаётся как число 999, но существование
объекта проверяется уже внутри view. Конвертер не обращается к хранилищу.
Ноль подходит конвертеру, отрицательное число с минусом — нет.

**Показать:** оба URL и тест
`test_converter_passes_integer_and_names_reverse` в [tests/test_web.py](tests/test_web.py).

## 9. Обработка запроса к главной странице

**Вопрос:** полный путь от URL до ответа главной страницы.

**Ответ:** браузер отправляет `GET /`. Django создаёт `HttpRequest`,
обрабатывает middleware и использует `ROOT_URLCONF="queryflow.urls"`.
Корневой `path("", include("homepage.urls"))` передаёт пустой путь
в приложение. Его `path("", views.index, name="index")` вызывает
`homepage.views.index(request)`. Функция формирует `content`, вызывает
`page("Главная", content)` и возвращает `HttpResponse` с кодом 200.
Django отправляет заголовки и тело ответа, браузер отображает HTML и стили.

## 10. Объекты request и response

**Вопрос:** откуда приходит `request`, что возвращает view и можно ли строку?

**Ответ:** объект `HttpRequest` создаёт Django на основании входящего запроса
и передаёт первым аргументом. Через него доступны `request.method`,
`request.path`, `request.GET`, заголовки и другие сведения.

```python
return HttpResponse(page("Главная", content))
```

Возвращается объект HTTP-ответа с телом, заголовками и статусом.
Браузер получает сериализованный HTTP-ответ, а не Python-объект.
Обычная строка не удовлетворяет контракту view: middleware и обработчик
ожидают атрибуты ответа, поэтому возникнет исключение и обычно HTTP 500.
`page()` может вернуть строку, потому что это вспомогательная функция;
view обязана обернуть её в `HttpResponse`.

## 11. Формирование HTML-страницы

**Вопрос:** где появляется `content`, где передаётся в `page()` и HTML?

**Ответ:** в [homepage/views.py](homepage/views.py), внутри `index()`,
`content` — строка с секцией приветствия, заголовком, описанием и ссылками.
Она передаётся вторым аргументом в `page("Главная", content)`.
Внутри `page()` строка вставляется в `<main class="container py-5">`.
Полученный документ становится телом `HttpResponse`.

Если передать другой `content`, поменяется содержимое `main`.
Навигация, подключение Bootstrap и footer сохранятся. Например,
`page("Проверка", "<h1>Новый текст</h1>")` создаст страницу с новым текстом.
Данные пользователей заранее проходят `escape()`, чтобы HTML-теги в данных
выводились текстом. Сам `content` — доверенная разметка приложения.

## 12. Назначение page()

**Вопрос:** зачем общий помощник и какие части он создаёт?

**Ответ:** `page(title, content)` устраняет копирование каркаса между view.
Он формирует `DOCTYPE`, `html lang="ru"`, `head`, кодировку UTF-8,
`viewport`, `title`, подключение Bootstrap, CSS, навигацию, `main` и footer.
Конкретная view передаёт заголовок вкладки и основную HTML-разметку.

В ПР5 HTML находится в строках по заданию. В следующей работе общий каркас
можно перенести в `base.html`, а данные передавать через контекст `render()`.

## 13. Повторное использование HTML-кода

**Вопрос:** сопоставить `page(title, content)` для двух страниц.

**Ответ:** `index()` вызывает `page("Главная", content)` и передаёт
описание проекта. `questions()` вызывает `page("Вопросы", content)`
и передаёт список объектов. В обоих случаях общие меню, стили и footer
одинаковы; различаются вкладка браузера и содержимое `main`.

**Показать:** [homepage/views.py](homepage/views.py),
[questions/views.py](questions/views.py), затем `/` и `/questions/`.
Изменение общей навигации в одном `page()` обновляет все страницы.

## 14. Изменение заголовка страницы

**Вопрос:** изменить заголовок одной страницы, не меняя общий каркас.

**Ответ и демонстрация:** в конце `questions()` временно заменить
`page("Вопросы", content)` на `page("Обсуждения", content)`.
Обновить `/questions/`: заголовок вкладки станет «Обсуждения | QueryFlow».
Меняется первый аргумент `title`.

Видимый заголовок `<h1>Вопросы</h1>` находится в `content` этой же view.
Чтобы изменить его, заменить только этот тег на `<h1>Обсуждения</h1>`.
Первый аргумент `page()` сам по себе **не меняет h1**.
После демонстрации вернуть обе строки. При обычном `runserver`
изменения Python подхватываются автоматически.

## 15. Bootstrap

**Вопрос:** где подключён Bootstrap, что дают классы и что будет без CSS?

**Ответ:** в `page()` переменная `bootstrap` содержит адрес Bootstrap 5.3.3
на CDN. `<link rel="stylesheet" href="...">` загружает таблицу стилей.
Используются `container`, `row`, `col-md-4`, `card`, `card-body`,
`list-group`, `list-group-item`, `btn`, `btn-primary`, `badge`,
`text-secondary`, `d-flex`, `flex-wrap` и классы отступов.

`row` и `col-md-4` дают три колонки на широком экране и вертикальное
расположение на узком. Если убрать `<link>`, HTML и ссылки останутся,
но Bootstrap-сетка, кнопки, отступы и типографика потеряют оформление.
Встроенный в `page()` собственный CSS продолжит работать.

**Показать:** `<link>` и классы в коде; в инструментах браузера временно
отключить ссылку CSS и сравнить. После демонстрации вернуть подключение.

## 16. Загрузка данных и поиск по ID

**Вопрос:** что возвращают функции загрузки и поиска, как используются во view?

**Ответ:** [storage.py](storage.py) содержит
`load_questions(categories, users)`, возвращающую `list[Question]`.
Она восстанавливает связи с объектами категорий и авторов.
В [models/questions.py](models/questions.py) функция
`get_question_by_id(questions, question_id)` возвращает `Question` либо `None`.

`question_detail()` сначала загружает категории и пользователей, затем
вопросы. После поиска проверяет `if question is None:`. Если объект есть,
использует его атрибуты и связанные ответы; иначе возвращает HTTP 404.
Загрузка даёт коллекцию, поиск — один объект или признак отсутствия.

## 17. Путь данных от JSON до представления

**Вопрос:** проследить путь от `data/questions.json` до HTML.

```text
question_detail(request, question_id)
  → load_categories() → Category
  → load_users() → User
  → load_questions(categories, users)
      → load_json("questions.json", []) → list[dict]
      → get_category_by_id(), get_user_by_id()
      → Question(...) → list[Question]
  → get_question_by_id(...) → Question или None
  → чтение атрибутов, escape(), content
  → page(title, content) → HttpResponse
```

**Ответ:** фактическое чтение JSON выполняется **внутри вызванной view**,
а не до маршрутизации. `DATA_DIR` вычисляется от расположения `storage.py`.
В JSON связи хранятся числами; загрузчик превращает их в ссылки на объекты.
Данные читаются заново на каждом запросе. Для отсутствующего файла загрузчик
возвращает пустой список; запись с отсутствующей категорией/автором пропускает.

## 18. Объект предметной области в представлении

**Вопрос:** как объект ПР3 используется во view?

**Ответ:** поиск возвращает сам объект `Question` из коллекции, без
преобразования в словарь. В `question_detail()` читаются `question.id`,
`question.text`, `question.category.name`, `question.author.name`,
`question.created_on`. Вызывается `question.status_text(len(related))`.
Результаты включаются в HTML. Например,
`{escape(question.author.name)}` показывает автора.

Связь `question.author` — объект `User`, а `question.category` — объект
`Category`. Код веб-слоя повторно использует предметную модель ПР3.
ORM-запроса `Question.objects.get()` здесь нет.

## 19. Преобразование атрибутов в HTML

**Вопрос:** как изменение значения отражается на странице, показать результат.

**Ответ:** в `question_detail()` выражение `{escape(question.text)}`
помещает текст вопроса в `h1`, а `{question.id}` — номер в карточку.
Если изменить `text` вопроса №1 в `data/questions.json` и обновить
`/questions/1/`, заголовок изменится. Если поменять имя автора в
`data/users.json`, изменятся страницы всех его вопросов и ответов.

**Демонстрация:** сохранить исходный текст, временно написать «Проверка
отображения данных из JSON», обновить страницу, затем вернуть исходный текст.
Сохранять корректный JSON в UTF-8. Менять только объект в памяти без
`save_questions()` недостаточно: следующий запрос заново читает файл.
Автоматическая безопасная демонстрация на временных данных:

```powershell
python -m pytest tests/test_web.py -k status_and_json_changes -v
```

## 20. Типы данных

**Вопрос:** какие реальные типы используются и как они выводятся?

| Значение | Python-тип | Использование |
| --- | --- | --- |
| `question.id` | `int` | Поиск, URL, номер карточки |
| `question.text` | `str` | Заголовок, экранирование |
| `question.is_closed` | `bool` | Вычисление статуса |
| `question.created_on` | `str` | Дата в ISO-формате `YYYY-MM-DD` |
| `question.category` | `Category` | Доступ к `name`, `is_active` |
| `question.author` | `User` | Доступ к имени автора |
| `questions_list` | `list[Question]` | Обход циклом и поиск |
| `len(related)` | `int` | Количество ответов и статус |

**Ответ:** в JSON числа читаются как `int`, текст — `str`, `true/false` —
`bool`. Загрузчик дополнительно приводит основные значения к нужным типам.
Дата в объектах этого проекта хранится строкой, а не `datetime`.
Тип `Question | None` обозначает два возможных результата поиска.

## 21. Полный механизм обработки 404

**Вопрос:** где задан обработчик и что возвращает `page_not_found()`?

**Ответ:** в корневом [queryflow/urls.py](queryflow/urls.py) на уровне модуля:

```python
handler404 = "homepage.views.page_not_found"
```

При неизвестном URL или исключении `Http404` Django находит этот обработчик
и при `DEBUG=False` вызывает `page_not_found(request, exception)`.
Функция формирует страницу через `page()` и возвращает
`HttpResponse(..., status=404)`. В браузере есть пояснение и кнопка на главную.
Параметр `exception` принимает причину ошибки; наружу она не выводится.
Объявление `handler404` в URLconf отдельного приложения не заменит корневой.

**Показать:** `/nonexistent/` при отключённой отладке и статус в Network.

## 22. Ошибка маршрута и отсутствие ресурса

**Вопрос:** чем различаются неизвестный путь и отсутствующий объект?

**Ответ:** `/questions/abc/` не соответствует `<int:question_id>/`,
поэтому view не вызывается. Django использует общую обработку 404.
`/questions/999/` соответствует маршруту: view запускается, но поиск
возвращает `None`. Наша view сама возвращает оформленный ответ 404.

`handler404` используется при ошибке разрешения маршрута либо `raise Http404`
при `DEBUG=False`. **Явный `return HttpResponse(..., status=404)` не вызывает
handler404 повторно**. Поэтому для отсутствующего вопроса видно
«Вопрос не найден», а для неизвестного пути — «Страница не найдена».
При `DEBUG=True` вместо общего handler показывается техническая страница,
но явно сформированный ответ отсутствующего объекта остаётся прежним.

## 23. Ветвление в представлении

**Вопрос:** что произойдёт, если убрать проверку после поиска?

```python
question = get_question_by_id(questions_list, question_id)
if question is None:
    # content с сообщением и ссылкой на список
    return HttpResponse(page("Вопрос не найден", content), status=404)
```

**Ответ:** `return` завершает view, поэтому дальнейший код работает только
с существующим объектом. Если убрать ветвление и запросить отсутствующий
ID, обращение к `question.id` или `question.category` вызовет
`AttributeError`: у `None` нет таких атрибутов. Вместо ожидаемой 404
получится ошибка сервера 500. Проверка отделяет нормальное отсутствие
ресурса от программной ошибки.

## 24. Обработка отсутствующего объекта

**Вопрос:** почему необходимо проверять `None` и какие ошибки возможны?

**Ответ:** функция поиска по контракту может не найти объект. `None`
не является пустым объектом `Question` и не имеет его методов/полей.
`question.text` даст `AttributeError`; ошибочное обращение `question["text"]`
к `None` даст `TypeError`. Проверяю `is None`, а не сравниваю ID с нулём:
ID сам по себе не доказывает наличие записи.

Такая же проверка есть в `category_detail()` и `answer_detail()`.
Альтернатива для общего оформления — `raise Http404`. В ПР5 оставлен
явный ответ, чтобы показывать отдельное сообщение для каждого типа объекта.

## 25. Изменение HTTP-статуса

**Вопрос:** временно вернуть 403 вместо 404, где менять и как проверить?

**Ответ и демонстрация:** в ветке `if question is None:` функции
`questions.views.question_detail()` временно заменить только `status=404`
на `status=403`:

```python
return HttpResponse(page("Вопрос не найден", content), status=403)
```

После обновления `/questions/999/` тело останется прежним, статус станет 403.
Проверить вкладку браузера DevTools → Network → запрос → Status Code,
либо выполнить (сервер должен быть запущен):

```powershell
curl.exe -s -o NUL -w "%{http_code}" http://127.0.0.1:8000/questions/999/
```

**404 Not Found** означает, что ресурс не найден. **403 Forbidden** означает,
что сервер понял запрос, но отказывает в доступе. Для отсутствующего вопроса
правилен 404. Замена — учебный эксперимент, после показа вернуть `status=404`
и запустить `python -m pytest -q`. Менять общий `handler404` для этого не нужно.
