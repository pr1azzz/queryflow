# ПР7 — шпаргалка по 25 пунктам таблицы оценивания

Источник: §7.6, страницы 50–51 «ПР7_Django_SQL.pdf».
В таблице 25 показателей, всего 1,5 балла. Пример Roomly адаптирован
к предметной области QueryFlow — вопросы, категории, авторы и ответы.

Главное отличие этапа: **сайт читает SQLite через sqlite3 и SQL, без Django ORM**.
Консольная версия и JSON сохранены. Служебный `db.sqlite3` Django не является
предметной базой: наша база — `data/queryflow.sqlite`.

Перед демонстрацией из корня проекта:

```powershell
.\.venv\Scripts\python.exe -X utf8 -m db.import_json
.\.venv\Scripts\python.exe manage.py runserver
```

Команды Python ниже можно выполнять в `python manage.py shell`, используя
Python виртуального окружения. SQL-команды — в установленном локальном CLI:

```powershell
.\.venv\tools\sqlite\sqlite3.exe data/queryflow.sqlite
```

В CLI `.headers on` включает заголовки, `.mode box` — табличный вывод,
`.tables` — список таблиц, `.schema` — схему, `.quit` — выход.
Все учебные изменения кода вернуть после демонстрации.

## 1. Проектирование структуры базы

**Показать:** `data/queryflow.sqlite` в SQLite Viewer и `sql/schema.sql`.
Есть четыре таблицы: `categories`, `users`, `questions`, `answers`.
Вопрос относится к категории и автору; ответ относится к вопросу и автору.
Одна категория имеет много вопросов, один вопрос — много ответов.
Связи реализованы идентификаторами, а не вложенными Python-объектами.
Повторяющиеся имена авторов не копируются в каждую запись вопроса.

## 2. Таблицы и связи

В `schema.sql`: `id INTEGER PRIMARY KEY` — уникальный идентификатор.
`questions.category_id REFERENCES categories(id)` и
`questions.author_id REFERENCES users(id)` — внешние ключи.
У `answers` есть FK на `questions.id` и `users.id`.
`NOT NULL` запрещает NULL, `CHECK` ограничивает признаки значениями 0/1,
`ON DELETE RESTRICT` защищает используемую родительскую запись.

```sql
PRAGMA foreign_key_list(questions);
PRAGMA foreign_key_check;
```

Для фактической проверки FK необходимо `PRAGMA foreign_keys=ON` на каждом
соединении. В приложении это делает `db.database.get_connection()`.

## 3. Создание базы и применение схемы

```powershell
.\.venv\Scripts\python.exe -m db.database
```

`initialize_database()` открывает файл с разрешением создания и выполняет
`connection.executescript()` с содержимым `sql/schema.sql`.
`CREATE TABLE IF NOT EXISTS` и `CREATE INDEX IF NOT EXISTS` позволяют
повторить команду без удаления данных и ошибки «таблица уже существует».
Это не система миграций: изменение структуры существующей таблицы требует
отдельной команды. Для демонстрации создания новой базы можно вызвать
`initialize_database('путь/к/временной.sqlite')`, сохранив рабочую базу.

## 4. Подключение из Python

```python
from contextlib import closing
from db.database import DB_PATH, get_connection

print(DB_PATH)
with closing(get_connection()) as conn:
    print([tuple(r) for r in conn.execute('PRAGMA database_list')])
    print(conn.execute('SELECT COUNT(*) FROM questions').fetchone()[0])
```

Абсолютный `DB_PATH` вычислен от расположения модуля, не от текущей папки.
`PRAGMA database_list` показывает реально открытый файл.
Обычное подключение использует `mode=rw`: опечатка в пути не создаст
незаметно пустую базу. `closing` гарантирует закрытие соединения.

## 5. Импорт JSON

**Показать:** `db/import_json.py`, функцию `import_data()`.
Данные читаются из четырёх JSON, проверяются и передаются в `executemany()`.
Порядок: категории → пользователи → вопросы → ответы, чтобы сначала
появились записи, на которые ссылаются внешние ключи.
`bool` преобразуется в 0/1, даты остаются ISO-строками.

Все записи импортируются одной транзакцией. Успех фиксируется,
ошибка вызывает откат. `ON CONFLICT(id) DO UPDATE` обновляет совпавшие ID.
Повторный импорт не дублирует записи и не удаляет добавленные отдельно
записи SQLite. Запуск: `python -m db.import_json` из корня проекта.

## 6. Проверка импорта

```sql
SELECT COUNT(*) FROM categories;
SELECT COUNT(*) FROM users;
SELECT COUNT(*) FROM questions;
SELECT COUNT(*) FROM answers;
PRAGMA foreign_key_check;
PRAGMA integrity_check;
```

В исходном наборе получено соответственно **6, 4, 2, 1**.
Сравнить с длиной списков в соответствующих JSON. Если количества не равны,
проверить правильность файла БД, исходных файлов, ошибки импорта и наличие
записей, добавленных отдельно. Совпадение количеств не гарантирует совпадение
содержимого — нужно также сверить ID и поля. `foreign_key_check` должен
вернуть пустой результат, `integrity_check` — `ok`.

## 7. SELECT и состав полей

```sql
SELECT id, text, created_on FROM questions ORDER BY created_on DESC, id DESC;
```

`SELECT` определяет столбцы, `FROM` — источник.
Если убрать `text`, результат больше не содержит текста, и шаблон
не сможет его вывести. Добавление поля расширит доступные данные,
но само по себе не добавит их на страницу: нужно обратиться к нему в шаблоне.
Полный запрос списка в проекте — `question_list` в `sql/queries.sql`.

## 8. WHERE и условие отбора

```sql
SELECT id, text FROM questions WHERE category_id = 1;
```

Заменить 1 на 2: результат будет содержать вопросы другой категории.
WHERE проверяет каждую строку до группировки.
В приложении запрос `category_questions` получает ID через `?`,
а результат показывается на `/categories/1/` или `/categories/2/`.

## 9. Отбор по состоянию

```sql
SELECT id, text, is_closed FROM questions WHERE is_closed = 0;
```

0 означает открытый вопрос, 1 — закрытый. Замена условия меняет набор
выбранных записей. Реальные запросы: `open_questions` и `active_categories`.
Страницы: `/questions/open/`, `/categories/active/`.
«Открытый» не обязательно означает «без ответов»; для второго сценария
используется `unanswered_questions` с `NOT EXISTS`.

## 10. JOIN связанных таблиц

```sql
SELECT q.id, q.text, c.name AS category_name, u.name AS author_name
FROM questions q
JOIN categories c ON c.id = q.category_id
JOIN users u ON u.id = q.author_id;
```

Каждому вопросу подбираются его категория и автор. `ON` задаёт соответствие
ключей; `AS` даёт уникальные имена столбцам с одинаковым названием `name`.
Демонстрация — `/questions/` и `/answers/`: `answer_list` соединяет сразу
ответы, вопросы, категории и пользователей.

## 11. Несколько условий

```sql
SELECT id, text FROM questions
WHERE category_id = 1 AND is_closed = 0 AND created_on >= '2026-09-19';
```

`AND` требует выполнения всех условий. Изменить начальную дату на
`2027-01-01`: в исходном наборе результат пустой. При одинаковом ISO-формате
`YYYY-MM-DD` строковое сравнение дат соответствует календарному порядку.
В веб-поиске комбинируются текст, категория и начальная дата;
дата проверяется через `date.fromisoformat()` до выполнения SQL.

## 12. COUNT

```sql
SELECT COUNT(*) AS total FROM questions WHERE is_closed = 0;
```

`COUNT(*)` считает строки и при отсутствии совпадений возвращает одну
строку со значением 0. `COUNT(column)` не считает NULL, а
`COUNT(DISTINCT author_id)` считает разных авторов.
Запросы `question_summary`, `answer_summary` показываются в статистике.
В отличие от COUNT, SUM по пустому набору даёт NULL: используется `COALESCE`.

## 13. GROUP BY

```sql
SELECT c.id, c.name, COUNT(q.id) AS questions_count
FROM categories c LEFT JOIN questions q ON q.category_id = c.id
GROUP BY c.id, c.name;
```

Каждая группа соответствует категории. `LEFT JOIN` сохраняет и категории
без вопросов; `COUNT(q.id)` даёт для них ноль. `COUNT(*)` здесь был бы ошибкой:
он посчитал бы строку категории с NULL на стороне вопроса.
Вторая группировка — `author_statistics`, число ответов каждого участника.
Обе показаны на `/questions/statistics/`.

## 14. HAVING

К предыдущему запросу добавить перед `;`:

```sql
HAVING COUNT(q.id) >= 1
```

Останутся категории хотя бы с одним вопросом. При пороге 2 исходная
выборка пуста. В интерфейсе изменить поле «Минимум вопросов в категории».
`WHERE` отбирает исходные строки, `HAVING` — группы после агрегации.
В `category_statistics` значение порога передаётся через `?`.

## 15. Параметризованные запросы

```python
from db.queries import fetch_all
rows = fetch_all('category_questions', (1,))
```

В SQL: `WHERE category_id = ?`. Значение передаётся отдельным параметром,
поэтому пользовательский ввод не становится SQL-кодом. F-строка вида
`WHERE text = '{user_input}'` опасна SQL-инъекцией и проблемами с кавычками.
Один параметр — кортеж `(value,)`, запятая обязательна.

В импорте f-строками собираются только фиксированные имена таблиц и полей
из константы `IMPORTS`; сами значения всегда передаются через `?`.
Заполнители не заменяют имена столбцов или таблиц.

## 16. Получение именованных результатов

`db/database.py` задаёт `connection.row_factory = sqlite3.Row`.
`fetchall()` возвращает список строк, `fetchone()` — одну строку или `None`.

```python
from db.queries import fetch_one
row = fetch_one('question_detail', (1,))
print(row['text'], row['category_name'], row['author_name'])
```

Во view поле читается `row['answers_count']`, в шаблоне —
`{{ question.author_name }}`. Это имена результатов SQL, а не ORM-атрибуты.
Использование имён уменьшает зависимость от порядка столбцов.

## 17. Страница списка объектов

Открыть `/questions/`, затем `questions/views.py`, функцию `questions()`.
`fetch_all('question_list')` выполняет SQL. `_cards()` добавляет структуру
контекста для существующего шаблона ПР6, не загружая JSON.
`render(..., {'cards': cards})` передаёт список в `question_list.html`,
цикл включает `question_card.html`. В карточке читаются поля SQLite.

## 18. Отфильтрованные записи

Открыть `/questions/open/`. Функция `open_questions()` вызывает одноимённый
SQL с `WHERE q.is_closed = 0`. Шаблон общий со списком всех вопросов,
а состав данных и заголовок отличаются. Для проверки сопоставить с
`SELECT id FROM questions WHERE is_closed = 0` в CLI.
Фильтрация выполняется базой, а не условием, скрывающим карточки в HTML.

## 19. Отображение связанных данных

На `/answers/1/` одновременно видны текст ответа, автор, исходный вопрос
и категория. Их даёт `answer_detail` с JOIN.
Шаблон `answers/answer_detail.html` использует `answer.author_name`,
`answer.question_text`, `answer.category_name`; `answer.question_id`
формирует ссылку через `{% url 'questions:detail' answer.question_id %}`.
Проверить соответствие этих имён псевдонимам в SELECT.

## 20. Пользовательский поиск

Открыть `/questions/search/`, ввести `Python`, категорию 1 и дату
`2026-09-19`. Форма GET отправляет `q`, `category`, `since`.
View получает их из `request.GET`, проверяет значения, выполняет
`question_search` и `search_count` с параметрами. Список результатов
передаётся в шаблон; выбранные значения остаются в форме.

`instr(lower(q.text), lower(?))` ищет буквальную подстроку. Регистр латиницы
игнорируется, кириллицы — учитывается стандартным SQLite.
`LIMIT 10` и `OFFSET` задают страницу, `ORDER BY created_on DESC, id DESC`
обеспечивает определённый порядок. Недопустимые параметры возвращают 400.

## 21. Статистика

Открыть `/questions/statistics/`. View выполняет `question_summary`,
`answer_summary`, `category_statistics`, `author_statistics`, `user_list`.
Шаблон получает одноимённые ключи контекста и отображает общие числа,
распределение вопросов и число ответов участников.
После исходного импорта: 2 вопроса (1 открыт, 1 закрыт), 1 ответ,
1 ответивший автор. Категории и участники без записей показаны с нулём.

## 22. Несовпадение контекста и шаблона

В `statistics()` ключ `'category_statistics'` соответствует циклу
`{% for item in category_statistics %}`. Временно переименовать только
ключ в `'stats'`: SQL продолжит возвращать данные, но шаблон увидит
пустую/отсутствующую переменную. Исправить имя в контексте или в шаблоне.
Проверять отдельно результат `fetch_all()` и переданный словарь,
не переписывать рабочий SQL из-за опечатки в DTL.

## 23. Пустые результаты

Найти `несуществующий-текст-123` или задать высокий порог статистики.
Запрос выполнится успешно, вернёт `[]`; шаблон покажет `{% empty %}`.
HTTP-статус — 200, потому что поиск обработан корректно.
Несуществующая карточка ID возвращает 404, неверные GET-параметры — 400.
Ошибка SQL, например неизвестный столбец, вызывает исключение,
а не пустой список: скрывать её под сообщением «ничего не найдено» нельзя.

## 24. Диагностика SQL

Неверное имя `SELECT unknown FROM questions` вызывает
`sqlite3.OperationalError: no such column`. Исправить на реальный столбец.
Ошибочный JOIN `ON q.id = c.id` может не вызвать исключения, но свяжет
не те записи; правильно `ON q.category_id = c.id`.
При неправильной выдаче сначала выполнить SQL отдельно, сверить ID,
условия, скобки AND/OR и число строк. Отдельно проверить, не исключил ли
WHERE строки с NULL после LEFT JOIN и не размножил ли JOIN записи.

## 25. Сквозная обработка запроса

```text
GET /questions/search/?q=Python&category=1&since=2026-09-19
→ queryflow/urls.py → questions/urls.py, name='search'
→ questions.views.search(request)
→ request.GET, проверка текста/ID/даты/страницы
→ параметры отдельно от SQL
→ db.queries.fetch_all('question_search', parameters)
→ db.database.get_connection(), sqlite3.Row, execute(), fetchall(), close()
→ контекст cards/total/q/category_value/since
→ questions/search.html → base.html и include карточки
→ HTML-ответ → браузер
```

Если результат неверен, последовательно проверить URL и параметры,
файл базы, SQL и значения параметров, строки результата, ключи контекста,
обращения в шаблоне. HTML и бизнес-данные не смешиваются со строкой SQL.
